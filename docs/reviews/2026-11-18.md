## Findings
### 1. Deleted check-ins can still upload and reappear
- Where: android/data/src/main/java/com/repknot/data/SessionSync.kt:51–54; android/data/src/main/java/com/repknot/data/CheckInStore.kt:70–71; android/app/src/main/java/com/repknot/app/ui/ProgressScreen.kt:136
- What: Sync snapshots pending rows before uploading them. Delete independently removes any pending row, including one already selected or being uploaded. Sync can therefore send a successfully deleted row; the next refresh restores it as an uploaded, non-deletable entry.
- Why it matters: Delete can appear successful while the unwanted measurement still reaches the server. The DAO test exercises deletion and acknowledgement sequentially, missing this interleaving.
- Suggestion: Serialize deletion with upload through the same synchronization boundary, checking row existence before sending. Add a delete-during-upload test.
- Confidence: high

### 2. Restoring a workout can override reminder navigation
- Where: android/app/src/main/java/com/repknot/app/AppNavigation.kt:34–48; android/app/src/main/java/com/repknot/app/MainActivity.kt:57
- What: A reminder tap sets `focused = false` and opens Body, then immediately consumes the request. If the persisted current session finishes loading afterward, the separate session effect sets `focused = true`, replacing Body with the logger.
- Why it matters: A cold-start reminder tap can open the workout instead of the promised check-in dialog. Existing reminder tests cover scheduling dates, not this navigation sequence.
- Suggestion: Keep the reminder destination pending until workout restoration completes, or suppress automatic logger focus when handling that destination. Test a reminder launch with delayed session loading.
- Confidence: high

### 3. Higher-load timed mismatches falsely count as recovery
- Where: android/domain/src/main/kotlin/com/repknot/domain/Progress.kt:200–207; android/domain/src/test/kotlin/com/repknot/domain/ProgressTest.kt:220–221
- What: When comparisons fail, the recovery fallback increments `evaluated` whenever the latest load exceeds the baseline maximum—even if the failure was a timed-versus-repetition mismatch. Task 037’s follow-up decision says such mismatches are not evaluated.
- Why it matters: Incomparable follow-ups can resolve a dip and remove its warning. The mismatch test uses a lower load, so it never exercises this branch.
- Suggestion: Require matching timed mode before applying the higher-load fallback. Add a higher-load timed-mismatch test.
- Confidence: high

### 4. Future unit changes erase historical dip labels
- Where: android/domain/src/main/kotlin/com/repknot/domain/Progress.kt:234–240; android/app/src/main/java/com/repknot/app/HistoryViewModel.kt:19,30
- What: `sessionDips` chooses each exercise’s unit from its latest exposure across the entire history, then filters every historical session through that unit. Appending sessions in another unit can remove previously detected dips; even a light session can change the chosen unit.
- Why it matters: The new History labels are not stable historical classifications. Later logging can silently remove both old labels and active dip alerts without recovery.
- Suggestion: Track previous exposures by exercise and unit while processing sessions chronologically, rather than choosing one future-derived unit. Test that appending a different-unit session preserves existing dip classifications.
- Confidence: high

### 5. The accepted sync ADR still describes superseded behavior
- Where: docs/decisions/001-sync-model.md:64,179–180,194–195; docs/architecture.md:103–116
- What: ADR 001 still specifies finish-confirmation uploads, rejects manual-only push, and describes History/Progress as online Supabase queries. Current architecture and implementation instead require explicit workout Upload and compute these screens from Room. The ADR has no supersession notice for these sections.
- Why it matters: A newcomer following the accepted sync decision receives conflicting instructions about upload intent and offline ownership.
- Suggestion: Annotate the superseded sections with links to task 028, ADR 004, and the current architecture, preserving the original rationale.
- Confidence: high
